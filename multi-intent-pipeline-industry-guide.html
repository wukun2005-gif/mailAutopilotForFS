MULTI-INTENT DETECTION · EMAIL / CUSTOMER SERVICE

多意图识别（Multi-Intent Detection）在邮件/客服场景的业界 Pipeline 与模型全景

从历史邮件建立意图目录，到新入站邮件的多意图识别、归因到目录、路由与处置：业界经典成熟做法、模型家族、评估与持续迭代的完整介绍。
适用：Email Autopilot for Financial Services 项目 · 生成日期 2026-10-17

0. 你的 pipeline 对吗

结论：对，方向正确，是业界的主干做法。「先从历史邮件建立意图目录（intent category list），再对新入站邮件做多意图识别，把识别出的意图归因到已有目录，然后路由与处置」——这就是业界标准的多意图识别（MID）+ 多标签分类（multi-label classification）+ 路由（routing）流水线。

但有 4 个缺口需要补，否则在金融/监管场景会出事：

  • 高危/受监管意图必须"只多不少"。对 Reg E/Z 等受监管意图，模型可以升级（model may upgrade）但绝不能被静默降级；需要一个高召回、低精度的规则层垫底（本项目已有 keywordDetector.ts），把模糊邮件路由到人工而非自动处置。
  • 必须显式处理"未知意图 / 新意图"。目录不是封闭集合；历史里没出现过的新意图需要被发现（聚类/新意图发现 NID）并进入审核，而不是被强行归入最近的类。
  • 多意图不是"挑一个"。归因时可能得到 0~N 个意图，处置策略是"任一受监管意图触发时钟"、"风险取最大（按维度）"、"需要人工的意图对应部分升级"，不能只取 top-1。
  • 置信度校准 + 证据链 + 人机回环。每个意图命中必须带证据句（evidence sentences）、置信度；按置信度三档路由（自动 / 缓冲复核 / 人工）；人工纠正回流训练。
映射到本项目：本项目的 INTENT_SPECS 目录 + recordedTriage 多意图输出 + keywordDetector 高召回安全网 + R×I×L 矩阵，已覆盖主干；缺口主要在"未知意图发现"、"置信度校准/三档路由显式化"、"评估指标落地"。

1. 问题定义

1.1 单意图 vs 多意图

  • 单意图分类（single-intent / multi-class）：一句话/一封邮件只属于一个类。大多数传统 IVR/聊天机器人假设。
  • 多意图识别（MID / multi-label）：一句话/一封邮件可同时包含 0~N 个意图。真实客户邮件的常态："我的卡还没到，另外我不认识这笔 $247.18 的扣款"。

1.2 邮件/客服场景的特殊性

  • 长文本 + 线程：一封邮件含多段、多轮回复；意图可能分布在不同轮次，新轮次可能追加新意图。
  • 隐含意图："我上周五付的账单怎么还没到"隐含"交易查询 + 可能的投诉"。
  • 受监管意图：半句话"我不认识这笔扣款"即构成 Reg E 错误通知， statutory clock 从入站时间起算。
  • 噪声：签名、免责声明、转发链、附件、OCR 文本。
  • 多语言、方言、错别字、口语化。

1.3 核心术语

Intent（意图）
用户想达成的目标/诉求，如" disputing a charge""refund fee"。
Slot / Entity
意图的参数，如金额 $247.18、账户、日期。
Taxonomy / Category list
意图目录，层级化、带风险/监管属性。
Attribution / Canonicalization
把识别出的自由文本意图映射到目录中的标准 code。
Routing
根据意图（及风险/身份/置信度）决定队列、SLA、处置方式。
OOD / Novel intent
目录外的新意图。

3. 模型家族全景

3.1 规则 / 关键词层（高召回安全网）

廉价、确定、可审计。业界在受监管意图（纠纷、欺诈、投诉）前放一层高召回规则：宁可假阳性（路由到人工）也不假阴性。本项目 keywordDetector.ts 即此层。适合：Reg E/Z 纠纷措辞、投诉关键词、欺诈信号。

3.2 传统 ML（TF-IDF + LR/SVM, fastText）

小数据、低延迟、可解释。多标签用 One-vs-Rest。fastText 训练快、部署轻。适合基线与资源受限场景。

3.3 深度学习（CNN / BiLSTM）

在 Transformer 普及前的主流；如今多作为轻量备选或蒸馏学生模型。

3.4 Transformer 预训练模型（BERT 家族）

当前生产主力。多标签分类：在 [CLS] 上接 sigmoid 多标签头（binary cross-entropy），或用 SetFit 小样本。DistilBERT/RoBERTa 常作蒸馏/精度权衡。金融/客服领域可继续在领域语料上预训练（domain-adaptive pretraining）。

3.5 联合意图-槽位（Joint Intent & Slot Filling, SLU）

同时做意图分类 + 槽位标注（BIO）。架构：BERT 编码 + intent 头 + slot 头，常加 slot-gated / co-interactive / stack propagation。适合需要参数抽取的场景（订票、转账）。代表：BERT-Joint、SLIM、NVIDIA NeMo Joint Intent & Slot。

3.6 多意图专用模型（MID）

专门针对"一句话多意图"。数据集：MixATIS、MixSNIPS（人工拼接，被批"不自然"）、BlendX（更自然的混合模式）。方法：多标签 BERT、注意力机制、生成式（BART/seq2seq 把意图集作为生成目标）、TFMN 等。生成式思路：把"识别意图"变成"生成意图列表"。

3.7 LLM（大语言模型）

零样本/少样本提示 + 结构化输出（JSON Schema / function calling）直接抽出意图列表与证据句。优势：冷启动、长尾、可解释；劣势：延迟、成本、幻觉、非确定性。生产中常见"LLM 候选 + 小模型/规则 adjudication"或"LLM 仅用于长尾/新意图"。结构化输出保证 schema 合法。

3.8 层级分类（Hierarchical）

先分大类（产品线/业务域 20+），再分小类（每域 30-40 意图）。降低单模型复杂度，提升可维护性。本项目 INTENT_SPECS 按业务域隐含分组。

3.9 新意图发现（Novel Intent Discovery, NID）

对目录外样本做聚类/对齐，发现新意图类别。方法：Deep Aligned Clustering、VAE OOD 检测、主动学习。生产中用于"目录扩展"与"长尾覆盖"。

3.10 OOD / 拒识（Out-of-Domain）

判断输入是否属于任一已知意图；低于阈值或 OOD 分数高 → 进入"未知/人工"。对安全至关重要。

5. 意图分类体系（Taxonomy）设计

  • 层级化：域（Domain）→ 产品线（Product）→ 意图（Intent）。例：银行 → 借记卡 → card_delivery_status / card_lock。
  • 原子性：一个意图对应一个可处置的动作/义务，避免"大杂烩"类。
  • 可共存性：明确哪些意图可共存（card_delivery_status + reg_e_intake），哪些互斥。
  • 监管属性：每个意图标 regulated: true/false、risk R0-R4、clockDriven、intakeAutoAtAnyIdentity。
  • 字段敏感度：fieldClass 控制回复时可披露字段（本项目已有）。
  • 版本化：policyPackId 绑定策略包版本，变更可追溯。
  • 粒度权衡：太粗 → 路由不准；太细 → 数据稀疏、模型难训。建议 20-60 个叶子意图起步。
本项目 INTENT_SPECS 是一个良好的 taxonomy 示例：code、risk、regulated、fieldClass、policyPackId、clockDriven。

6. 归因（Attribution）与规范化

  • Alias 映射：模型/LLM 输出的自由短语 → canonical code（同义词表）。
  • 去重与合并：同一意图多次命中合并；证据句聚合。
  • 层级归类：叶子 → 父类，便于报表与路由。
  • 置信度校准：原始分数 → 可靠概率（Platt/Isotonic/Temperature scaling）。
  • 证据链：每个命中附 evidenceSentences，支持审计与人工复核。
  • 否定/排除：识别"不是 X"避免误标（如"这不是欺诈"）。
  • OOD 检测：置信度低于阈值或 OOD 分数高 → 标记 unknown，进新意图发现。

7. 路由与处置

7.1 置信度三档

档位条件动作
自动（Auto）置信度 ≥ 高阈值 且 风险 ≤ 允许等级自动处置（clock、收据、材料追逐）
缓冲复核（Review）中等置信度 或 高风险意图AI 草拟，人工一键确认
人工（Human）低置信度 / OOD / 高风险 R3+ / 欺诈信号升级人工，AI 仅提供证据

7.2 多意图聚合策略

  • 风险取最大（按维度，非按整封邮件）：聚合作用于同一回复内容里的字段敏感度/风险等维度，决定该部分内容可披露/可自动发送的门槛；不是把整封邮件所有意图都升级。各意图的处置仍分别执行。
  • 任一受监管触发时钟：reg_e_intake 命中 → 立即启动 Reg E clock，不论其他意图。
  • 任一需要人工 → 对应部分升级：contact_detail_change (R3) 命中 → 其对应处置/回复部分升级人工；低风险意图（如 card delivery）仍可自动回复。
  • 处置可并行：各意图的 intake 可并行执行（如同时 clock + 材料追逐）。

7.3 身份与自治（R×I×L）

路由不仅看意图，还看身份保障级别 I 与自治等级 L：同一意图在 I0（未验证）与 I3（强验证）下处置不同；自治等级按意图毕业（graduation）逐步提升，可收紧/放宽。

8. 评估指标

  • Subset Accuracy（子集准确率）：预测集合与真实集合完全一致的比例。严格。
  • Hamming Loss：标签级错误率，允许部分正确。
  • Micro/Macro F1、Precision、Recall：多标签标准。
  • Per-intent Recall（尤其受监管意图）：Reg E/Z 意图 recall 必须 ≈ 1.0（假阴性代价极高）。
  • OOD 检测：AUROC、FPR@95TPR。
  • 业务指标：自动处置率、人工升级率、SLA 达成率、误处置率、客户满意度。
  • 延迟与成本：p95 延迟、每封成本。
关键：对受监管意图，优化目标是 recall 而非整体 accuracy；允许假阳性（路由人工）。

10. 邮件/金融场景的特殊考量

  • Reg E/Z 合规时钟：错误通知 = 入站邮件；clock 从入站时间起算，必须在 intake 阶段就启动，不能等分类完成。
  • 高召回安全网：受监管意图前放关键词层；模型可升级不可静默降级。
  • 线程上下文：新轮次可能追加意图；需 thread-level 聚合 + 增量检测。
  • PII 与安全：脱敏、附件 prompt-injection 当数据处理、lookalike 地址检测。
  • 多语言：语言检测 + 多语言模型或翻译。
  • 附件/OCR：OCR 文本单独通道，避免污染正文意图。
  • 欺诈/BEC：并行筛查，不串行。
  • 审计：证据句、置信度、模型版本、策略包版本全留痕。

11. 数据工程与持续迭代

  • 标注指南：意图定义、边界案例、多标签标注规范、标注者一致性（Cohen's kappa）。
  • 主动学习：优先标注低置信/高分歧样本。
  • 人机回环：人工纠正 → 标注池 → 增量训练。
  • 漂移监控：意图分布、置信度分布、新词/新短语、OOD 率。
  • 发布门禁：backtest → shadow → 双签（Product + Compliance）→ 渐进放量；收紧可当日生效带自动过期，放宽必须 earned。
  • 数据集：MixATIS/MixSNIPS/BlendX 用于基准；生产用真实邮件标注。

13. OOD / 新意图治理：客户 vs 供应商分工

银行上线后 inevitably 会出现目录外的新意图（OOD）。谁来解决、怎么解决，决定售后能否规模化。

13.1 客户（银行 IT/admin）能通过 config 解决的

  • 新增意图 code、别名/同义词、关键词规则、路由策略、SLA、回复模板、阈值。
  • 前提：检测层用 LLM 提示/零样本或可扩展 taxonomy 驱动——意图目录存在配置/数据库里，检测时动态读取；新增意图 = 改配置，不改模型权重。
  • 银行 admin 通过界面填：意图名称、描述、示例、关键词、路由。系统自动生成 prompt，银行不手写 prompt。
  • 新意图先以"候选"状态出现（LLM 零样本或聚类发现），由人审核确认名称/定义/路由后才正式写入目录；确认前保持"未知/待审"，路由到人工复核。

13.2 供应商（Talkdesk）必须介入的

  • 基础模型无法区分新意图（embedding 重叠、性能明显下降）时，需重训。
  • 但不应"每银行各训一次"。正确做法：共享的 vertical foundation model + 多租户 config；新意图先走 LLM 零样本/规则兜底；Talkdesk 把各银行上报的新意图聚类、匿名化聚合后，批量、周期性重训一次共享模型，所有银行同步升级。

13.3 为什么这样不会让售后崩溃

  • config 优先覆盖 80%+ 的新意图诉求，银行自助。
  • 重训是中央批量、周期性、共享模型，不是按客户定制。
  • 如果每个银行都要单独重训 vertical model，售后必然崩溃；架构上必须避免。
反模式：把意图写死在模型权重里、按客户定制模型、无候选/审核流程直接自动入库。
