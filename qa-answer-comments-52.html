4. 发现的问题

观察 ② 半数回答只用了 1 个知识块，上下文偏薄

52 条里 25 条只有 1 个块进 prompt，中位数为 1，最多也只用到 4 个。数字都能对上来源（§5 的严格校验 0 例外），但回答的「厚度」受此限制——有些本该展开的问题只能给出一句结论加一个 caveat。

位置在重排之后的筛选：动态阈值 0.7×top 加上绝对下限 0.1，再经 MMR λ=0.7 去重。当 top-1 明显领先时，0.7 阈值会把第 2、3 名全部砍掉。可调、也可只在「单块回答」时放宽，属产品判断，未擅自改。

观察 ① 3 条英文提问得到中文回答

提示词里写得很清楚（index.ts:474）：Answer in the same language the comment is written in — a Chinese comment gets a Chinese answer, an English comment gets an English answer. 但这一轮有 3/52（6%）违反：题干是英文，答案用中文。

根因是语言镜像，不是随机波动：这 3 条全部引用了中文的《调研报告》，而 52 条里没有任何一条「不引用该报告却用中文作答」。交叉表如下——显然不是纯巧合：

引用了调研报告未引用
答案用中文30
答案用英文940

《调研报告》原文是中文（该源 CJK 占比 38.4%，Deck 与 PRD 是 0%）。当答案的主要依据来自它时，模型会被源文语言带走。出问题的是三处：p2 · SPM、p3 · PE、p12 · PPM。

这条不影响准确性（引用与数字都没错），影响的是读者体验：一份英文 deck 的英文提问收到中文答案。修法可以是在 System 段把语言规则再强调一次并给反例，或者在检索阶段把「与提问语言不一致的块」降权。未改，等 owner 决定。

好现象 5 条答案主动声明「材料未覆盖」，没有编造

碰到材料确实答不了的部分时，模型选择说明边界而不是糊过去，并且仍然给了它确实找得到的部分。这是期望行为——deck 是内部案例，很多实施细节本来就没写。

5. 数字可追溯性：严格校验

初版脚本在做「答案里的数字能否在材料里找到」时，一旦块 key 对不上就回退到整篇文档——那样几乎任何数字都能被「找到」，指标形同虚设。改成只在该题实际检索到的块里查之后：

检查结果
答案含无法在检索到的块中定位的数字0 条
来源章节在知识库里找不到对应块0 条

这一轮答案里出现的全部数字（含 262、$4.8M、≥99.5%、n≥600、Reg E 1005.11(b)(1) 等）都能回到检索到的原文。

R3 is never autonomous over email because the tool functions do not exist on this channel. Is that an architectural guarantee, or a deployment choice someone could reverse later?

It is architectural: the R3 tool functions are simply not registered on the email channel, so security rests on unreachability rather than model obedience (see [4](https://wukun2005-gif.github.io/mailAutopilotForFS/email-autopilot-fs-prd_en.html), FR-6.3 AC1). Reversing it would require a deliberate platform change, not a config toggle, but nothing in the reference material rules out a future product decision to add such functions; the guarantee holds for the current design.

6.2 主动声明边界（5 条中的 2 条）

第 9 页Senior Engineer1 块 · 4.0s

Admin tightens a limit in one click. Does that write a new policy version or mutate the live one, and can it be rolled back?

Admin actions always produce a configuration diff — a new policy version, never a mutation of the live one. The bank signs it through the same gates as any other change (see [1](https://wukun2005-gif.github.io/mailAutopilotForFS/deck-html/)). Rollback is inherent: since every change is a versioned diff, reverting is just applying the prior diff — but note the deck doesn't specify a rollback UI or SLA, so I can't speak to operational details beyond that.
Sources: 1. [Case Study Deck — Admin: the bank writes the limits, not the model.](https://wukun2005-gif.github.io/mailAutopilotForFS/deck-html/)
第 13 页PM line VP2 块 · 6.3s

Sign-off fatigue is on the register. What stops one-click approvals from becoming rubber stamps once a customer is running at the target autonomy?

Good catch — the register flags it, but the deck doesn't claim a hard stop. The mitigation is the same one shown in the prototype: the autonomy cell downgrades from auto to one-click when the policy condition fails, and the reason is only readable on the agent screen (see [2](https://github.com/wukun2005-gif/mailAutopilotForFS/blob/main/src/demo/scripts.ts)). We track the approve-without-edit rate and sample approved files, but we don't promise a threshold that eliminates rubber-stamping — that's a live risk, not a solved one (see [1](https://wukun2005-gif.github.io/mailAutopilotForFS/deck-html/)).
